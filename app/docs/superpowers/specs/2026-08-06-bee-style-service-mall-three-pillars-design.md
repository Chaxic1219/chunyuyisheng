# 服务包商城（bee 风格）× 三支柱并列 — 设计规格

**日期：** 2026-08-06  
**状态：** 已批准（主人 2026-08-06「继续」）；S1 已实现（自动化验收通过 2026-08-06）  
**范围：** 患者小程序 + 管理后台 + `servicePackage` 域  
**参考：** [woniudiancang/bee](https://github.com/woniudiancang/bee)（仅借鉴信息架构与交易闭环，不接入 api工厂）  
**前提决策：**

- 集成方式 **A**：在现有自建 `servicePackage` 上对齐 bee 交互，不替换医患主链  
- 支付红线先定为真微信支付，商户材料按 **C**（后配可开）；支付落在 **S4**  
- 能力范围 **P3**（含购物车、优惠券等），**分期交付 S1–S6**  
- **保留**现有小程序以健康档案、AI 对话咨询为主的逻辑；服务包购买与消费与二者**同等重要**

---

## 1. 产品定位

春雨医患通小程序为**三支柱并列**产品，而非纯商城：

| 支柱 | 权重 | 主职责 | 主入口（保持/强化，不削弱） |
|------|------|--------|----------------------------|
| 健康档案 | 同等 | 建档、记录、计划素材 | 首页快捷、档案页、我的相关入口 |
| AI 对话咨询 | 同等 | 问诊对话、上下文延续 | 底部咨询 Tab |
| 服务包（商品服务） | 同等 | 选购、支付、审核开通、履约消费 | 首页推荐大卡、健康服务、目录/订单/我的服务 |

**硬约束：**

1. 不把 Tab 改成 bee 餐饮五栏（首页/点餐/取号/取餐/我的）。  
2. 现有 Tab（首页 / 咨询 / 我的）与档案、咨询主链路在任一期不得回退或降级为附属。  
3. bee 只塑造**服务包支柱**的页面与交易逻辑；档案与咨询独立演进，S6 再做三支柱互带。  
4. 不接入 bee 依赖的 api工厂 / `admin.s2m.cc`；后端继续自建 Node + SQLite（或后续同源库）。

## 2. 明确不做（全周期）

| bee 能力 | 处理 |
|----------|------|
| 桌号 / 扫码点餐 | 不做 |
| 叫号排队 / 取餐码核销 | 不做 |
| 达达等外卖配送 | 不做（服务包收货地址仅用于实体物料时保留字段） |
| 门店自提核销 | 不做 |

**语义映射：** bee「门店」→ 春雨「当前服务医生」；bee「菜品」→「服务包商品」；bee「取餐/履约」→「服务实例 + 康复计划/任务」。

## 3. 分期总览（P3）

| 期 | 名称 | 目标 | 支付 | 可对外验收 |
|----|------|------|------|------------|
| **S1** | 商城骨架 | bee 式单品选购 + 订单中心；三入口同级可见 | mock | 是（运营走查） |
| **S2** | 购物车 | 多服务包一次结算 | mock | 是 |

每期完成定义（DoD）必须包含：**档案页可打开、咨询 Tab 可对话、服务包本期能力可用**。

## 4. S1 详细设计（本期规格正文）

### 4.1 用户主链路

```text
[选医生] → 服务包目录(分类 | 列表) → 详情 → 立即购买
        → 确认订单(协议 / 联系方式 / 服务端计价) → 支付(mock) → 支付结果
        → 我的订单(状态 Tab) → 订单详情(进度)
        → 术后资料 → 待审核 → 我的服务(实例 / 履约)
```

并行保留：

```text
首页 → 健康档案 | AI 咨询 Tab | 服务包入口（权重视觉同级）
```

### 4.2 小程序页面（服务包侧）

| 页面 | 作用 | 相对现状 |
|------|------|----------|
| 服务包目录 | 分类 + 列表（bee 点餐列表感） | 强化 `catalog`，支持分类 |
| 服务包详情 | 封面、价格拆分、须知、购买 CTA | 强化 `detail` |
| 确认订单 | 协议勾选、联系人/地址、金额只读 | 强化 `checkout` |
| 支付结果 | 成功/待支付/失败引导 | 保留 `pay-result` |
| 我的订单 | Tab：待付款 / 待资料 / 审核中 / 已开通 / 退款相关 | **新建**（bee `all-orders`） |
| 订单详情 | 状态进度条 + 操作（去支付 / 填资料 / 看服务） | **新建或扩**现有订单查询 |
| 健康服务中心 | 医生切换 + 快捷入口 + 指向目录/订单 | 保留并与目录分工清晰 |
| 我的服务 | 已开通实例列表 | 保留 `mine-services` |

**入口同级（S1 必做）：**

- 首页：档案、计划/服务、咨询不削弱；服务包（医生管家/目录）与档案入口视觉权重对齐。  
- 我的：增加「我的订单」「我的服务」并列入口。  
- 不新增第四商城 Tab。

### 4.3 管理后台（S1）

| 模块 | S1 能力 |
|------|---------|
| 服务包商品 | 分类、封面图字段、标题/价格/医生归属、上下架、版本发布（沿用现有 version 模型） |
| 服务订单 | 按状态筛选、详情抽屉、催补资料、通过开通、驳回退款（mock） |
| 不改 | 档案审核、咨询坐席等非商品主链（除非 bug） |

### 4.4 后端（S1）

- 商品：增加/使用 **分类**（category）字段；列表支持 `doctorId` + `category`。  
- 订单：患者侧 **订单列表** API（分页 + 状态筛选）；详情含进度所需字段。  
- 金额：继续服务端按 `svc_product_versions` 计价，禁止信任前端金额。  
- 状态机保持：

```text
pending_payment → paid_pending_profile → pending_review → active
pending_payment → closed_timeout
paid_* / pending_review → refunding → refunded
```

- 支付：默认 `SERVICE_PAY_PROVIDER=mock`；接口形状预留 wechat（见现有 `service-package-payment-provider.md`）。

### 4.5 S1 验收清单

- [ ] 三支柱入口均可到达，档案与咨询无功能回退  
- [ ] 目录分类切换 + 详情 + 下单 + mock 支付 + 支付结果  
- [ ] 我的订单 Tab 与订单详情进度正确  
- [ ] 管理端可上架/下架、按医生筛选、审核通过/驳回  
- [ ] 开通后出现在我的服务

## 5. S2–S6 里程碑（详规分期另开文档）

### S2 购物车

- 小程序：购物车页、数量、结算生成**多行订单**。  
- 后端：订单行表或 JSON lines 快照；总价服务端汇总。  
- 后台：订单详情展示多行。  
- 约束：同一订单仅允许**同一服务医生**下的包（跨医生不可混结）。

### S3 营销

- 券模板、领取、下单选用、核销；权益页对接真实数据。  
- 后台：券 CRUD、发放、核销记录。  
- 结算价 = 服务端（商品快照 − 券）。

### S4 真支付（红线）

- 推荐：SDK 封装 `providers/wechat.js`（APIv3）：`create` / `query` / `handleNotify` / `refund`。  
- 环境变量仅服务端；缺配置时明确失败，不假成功。  
- `POST /api/mp/payments/wechat/notify` 验签幂等入账。  
- 小程序：`provider=wechat` 时 `uni.requestPayment`，再轮询 `payment-status`；**不以**前端成功为最终入账。  
- 退款：支持 `processing` → 查单/回调至 `refunded`。  
- 商户材料后配（决策 C）；文档与开关页在后台只读说明。

### S5 售后与资产感

- 退款申请页、进度；开通后部分退走人工审核。  
- 「服务资产」轻量页：有效实例、剩余权益摘要。  
- 后台：售后工单列表。

### S6 三支柱打通 + 其它优化

- 咨询可带入「当前服务实例 / 已购包」上下文。  
- 档案与服务实例关联展示。  
- 首页与健康服务视觉统一、字号与可达性与近期改版一致。  
- 其它医患功能按优先级排期，**不得压过**三支柱稳定。

## 6. 技术约束

| 项 | 约定 |
|----|------|
| 前端 | 现有 `patient-uniapp`（uni-app） |
| 后台 | 现有 `admin-ui` |

## 7. 风险与依赖

| 风险 | 缓解 |
|------|------|
| P3 范围过大导致档案/咨询被挤占 | 每期 DoD 强制三支柱检查；S2+ 单独开规格 |
| 真支付商户未齐 | S4 可开发与联调，上线开关与配置绑定 |
| 购物车与「单医生」冲突 | S2 强制同医生结算 |
| 优惠券规则复杂 | S3 先做满减/折扣两类，不做叠加战 |
