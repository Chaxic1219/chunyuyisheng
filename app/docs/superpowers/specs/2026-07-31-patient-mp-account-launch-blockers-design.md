# 患者微信小程序账号上线阻断项修复设计

日期：2026-07-31

## 1. 背景与目标

本次修复覆盖患者微信小程序、Node.js 后端以及二者之间的账号、邀请、问诊、AI 和资料传输链路。目标是在不改变现有主要产品流程的前提下，关闭正式上线前已经确认的身份冒用、会话膨胀、匿名资源滥用、敏感数据误传和隐私权入口失效问题。

成功标准：

1. 同一微信 OpenID 在正常登录后仅保留一个有效小程序会话。
2. 登录必须绑定有效医生上下文，前端并发生命周期不能制造无医生会话。
3. 换绑手机号只有在新号码验证成功后才原子生效，失败不影响原绑定。
4. 邀请链接不能仅凭链接和手机号覆盖既有患者资料或取得患者会话。
5. AI、问诊和凭证上传均要求有效身份；敏感数据发送 AI 前获得明确授权。
6. 生产构建不展示当前不可用的短信路径。
7. 数据导出和删除入口会创建真实、可追踪的后台申请。
8. 客户端不长期明文缓存完整身份证号、手机号和完整 AI 对话。
9. 相关回归测试、类型检查和微信小程序构建全部通过。

## 2. 非目标

- 本次不重做完整的患者中心、医生管理后台或隐私运营后台。
- 本次不自动执行不可逆的患者数据删除，只建立经认证的申请和审核记录。
- 本次不改变现有患者、人员、医生的核心表关系。
- 本次不在生产服务器执行部署、数据库清理或重启；生产变更需在本地验证完成后单独确认。
- 本次不接入新的短信供应商。短信未配置时相关流程必须安全失败。

## 3. 已确认的根因

### 3.1 登录与会话

- 首页 `onMounted` 与 `onShow` 都可能触发初始化和登录，形成并发请求。
- 登录可能在医生上下文加载完成前发生，因此服务器产生 `doctor_id` 为空的会话。
- 后端每次登录都创建新的 90 天会话，没有复用或撤销同一 OpenID 的旧会话。
- 生产数据已出现单个 OpenID 持有大量活动会话，以及真实微信会话缺少医生和患者上下文。

### 3.2 邀请资料

- 邀请提交当前仅依赖邀请令牌、手机号和同意勾选。
- 后端会按已验证手机号合并人员，并覆盖患者资料后签发患者会话。
- 因此获得邀请链接的人可以输入他人手机号，修改既有档案并获得对应患者访问身份。

### 3.3 AI、问诊和上传

- 线上 AI 路由仍允许匿名请求；本地已有认证修改但尚未部署。
- 问诊发送前没有统一保证登录态，401 后也没有进入恢复登录流程。
- AI 对话可能包含病情、身份证明等敏感内容，目前没有单独授权。
- 就诊凭证上传接口未认证，上传文件位于公开静态目录。
- 登录、AI 和上传缺少请求频率限制。

### 3.4 隐私与生产能力

- 短信供应商未配置，但客户端仍可能向用户展示短信备用入口。
- 数据导出、删除和授权管理目前只是提示弹窗，没有后台记录。
- 小程序本地缓存包含完整手机号、身份证号、健康资料和 AI 对话。
- 换绑流程先解除旧绑定；新号码验证失败时，用户会失去原有访问能力。

## 4. 总体设计原则

1. 服务器身份为唯一可信源，客户端缓存只用于展示和短期恢复。
2. 所有身份切换采用“先验证、后事务提交”，不先破坏旧状态。
3. 所有写操作按最小权限校验人员、患者和医生归属。
4. 安全能力缺失时失败关闭，不通过弱化验证维持流程可用。
5. 敏感正文尽量不新增持久化，只记录必要的安全审计元数据。
6. 保持现有 API 结构，新增字段和路由采用兼容式扩展。

## 5. 详细方案

### 5.1 登录单飞与单会话

客户端：

- 将首页启动合并为单一初始化 Promise。`onMounted` 和 `onShow` 只能复用该 Promise，不能并发执行登录。
- 先获取 bootstrap 和有效医生，再调用 `ensureLogin`。
- `ensureLogin` 自身增加单飞锁，同一时刻只允许一个 `wx.login` 和后端登录请求。
- 医生缺失时不发登录请求，展示可恢复错误状态。
- 收到 401 时清理失效令牌并重新走单飞登录；不无限自动重试。

后端：

- 登录请求必须携带有效、启用状态的医生标识；缺失返回 `400 doctor_required`，无效返回 `403 doctor_unavailable`。
- 在事务内按 OpenID 撤销现有活动会话，再创建一个新会话。
- 新会话复用已绑定的人员，并解析该人员在当前医生下的患者记录。
- 每次成功登录均轮换令牌，避免并发终端继续使用旧令牌。
- 数据库继续保存历史会话记录，但旧会话立即标记失效，不参与认证。

并发保证：

- 同一 OpenID 的登录事务使用数据库写事务串行化。
- 两个几乎同时完成的登录请求中，只有最后签发的令牌有效。

### 5.2 手机号首次绑定与原子换绑

首次绑定沿用微信手机号能力或短信验证码，成功后在事务内完成：

1. 校验当前小程序会话和 OpenID。
2. 校验新手机号的可信来源。
3. 找到或创建对应人员。
4. 将 OpenID 绑定到目标人员。
5. 关联当前医生下的患者记录。
6. 撤销旧会话并签发包含新身份的会话。

换绑不再先调用解绑接口。客户端进入 `rebind` 模式并保留当前令牌与原绑定，只有新手机号验证成功后才提交切换。

后端换绑事务：

1. 锁定当前会话、当前人员和目标手机号人员。
2. 再次验证手机号凭证，且凭证只能使用一次。
3. 清除旧人员的 `mp_openid`。
4. 将 OpenID 绑定到目标人员。
5. 解析目标人员在当前医生下的患者记录。
6. 撤销该 OpenID 的全部旧会话，签发新令牌。

任一步失败均回滚，原人员、原患者和原令牌保持可用。目标手机号已绑定其他 OpenID 时返回 `409 phone_already_bound`，不自动抢占。

### 5.3 邀请链接身份验证

邀请令牌只证明“可填写某位医生发出的邀请”，不能证明填写者是谁。

提交邀请资料时必须满足以下任一条件：

- 携带有效小程序 Bearer 会话，且会话绑定的已验证手机号与提交手机号一致。
- 携带有效患者网页会话，且其已验证手机号与提交手机号一致。
- 提供本次流程验证通过、未过期且未使用的短信验证码凭证。

不满足时返回 `401 phone_verification_required`。登录手机号与提交手机号不一致时返回 `403 phone_mismatch`。

只有身份验证通过后，后端才允许按手机号合并人员、更新患者档案和签发或刷新患者网页会话。短信未配置时，匿名邀请页明确提示需从微信小程序完成身份绑定，不提供绕过入口。

邀请详情接口提供验证能力状态，但不泄露目标患者是否存在：

```json
{
  "requireSms": true,
  "allowBoundSession": true,
  "smsAvailable": false
}
```

### 5.4 AI 与问诊

AI：

- 保留本地已实现的 Bearer 认证，线上部署时必须同步。
- 请求新增 `sensitiveDataConsent: true` 和授权版本，例如 `2026-07-31`。
- 客户端首次向 AI 发送内容前展示独立授权；拒绝后不发请求。
- 授权按账号保存，不保存于未绑定账号的公共缓存；版本变化时重新授权。
- 服务端拒绝缺少授权标记的请求，返回 `403 ai_consent_required`。
- 按会话和 OpenID 限频，超限返回 `429 rate_limited` 和 `Retry-After`。
- 不持久化对话正文。仅记录请求时间、人员、患者、会话、模型、字符数、结果状态和错误类别，用于安全审计。

问诊：

- 发送前统一调用 `ensureLogin`。
- 401 时停止发送、清理失效令牌并引导恢复登录。
- 客户端不得把未认证请求静默降级为本地成功状态。

### 5.5 就诊凭证上传与读取

- 上传要求有效 Bearer 会话。
- 请求中的医生、患者必须与会话解析出的医生和患者一致，客户端传入的身份字段不能覆盖服务器身份。
- 未绑定患者不可上传，返回 `403 patient_binding_required`。
- 按会话和 IP 组合限频，并保留现有文件类型、大小限制。
- 新文件存储到非静态公开目录，数据库只保存受控文件标识和必要元数据。
- 读取通过认证下载路由完成；患者只能读取自己的文件，管理端沿用现有管理员认证并校验业务权限。
- 响应使用安全文件名与 `Content-Disposition`，不返回真实磁盘路径。
- 旧公开文件不在本次本地实现中自动移动或删除，生产部署阶段单独盘点和迁移。

### 5.6 短信生产开关

- 当前短信供应商未配置，生产构建固定使用微信手机号绑定模式。
- 客户端不显示“短信备用验证”按钮。
- 后端短信接口继续拒绝生产请求，并返回稳定错误码 `sms_unavailable`。
- 后续只有在供应商配置、发送回执、验证码存储和限频全部验证后，才能开启短信入口。

### 5.7 数据导出与删除申请

新增 `mp_data_requests` 表：

- `id`
- `person_id`
- `patient_id`
- `request_type`：`export` 或 `delete`
- `status`：`pending`、`processing`、`completed`、`rejected`
- `created_at`
- `updated_at`
- `completed_at`
- `operator_id`
- `note`

新增接口：

- `POST /api/mp/data-requests`：创建申请。
- `GET /api/mp/data-requests/mine`：查询当前账号申请状态。

两者都要求有效且已绑定的 Bearer 会话。同一类型已有 `pending` 或 `processing` 申请时返回已有记录，不重复创建。

设置页的导出和删除按钮调用真实接口并显示申请编号和状态。删除申请不立即删除任何数据；必须经过后台人工审核、合规留存判断和独立执行。

### 5.8 客户端敏感缓存收敛

- 本地长期状态只保留令牌、人员/患者内部标识、脱敏手机号和必要展示字段。
- 完整身份证号不写入长期 storage；进入编辑页时从认证接口读取，离开页面后释放。
- 完整手机号不作为身份判断依据，所有权限以服务器会话为准。
- AI 对话默认只保留当前页面内存；若保留恢复能力，只保存非敏感摘要和时间，不保存完整正文。
- 退出、解绑或身份轮换时清理旧账号作用域下的缓存。

### 5.9 请求频率限制

使用现有单实例部署可接受的进程内固定窗口限频器，范围只覆盖本次高风险接口：

- 登录：按 IP 与 OpenID 组合。
- AI：按会话与 OpenID 组合。
- 上传：按会话与 IP 组合。

限频器提供统一 `429 rate_limited` 响应和 `Retry-After`。该方案在进程重启后重置，适合当前单实例；未来扩容到多实例时迁移到 Redis，不在本次引入新基础设施。

## 6. API 错误契约

| HTTP | 错误码 | 含义 |
| --- | --- | --- |
| 400 | `doctor_required` | 登录缺少医生上下文 |
| 401 | `unauthorized` | 令牌缺失、失效或已被轮换 |
| 401 | `phone_verification_required` | 邀请提交缺少可信手机号证明 |
| 403 | `doctor_unavailable` | 医生不存在或不可用 |
| 403 | `phone_mismatch` | 已验证手机号与提交手机号不一致 |
| 403 | `ai_consent_required` | 未确认 AI 敏感数据授权 |
| 403 | `patient_binding_required` | 操作要求已绑定患者 |
| 409 | `phone_already_bound` | 目标手机号已绑定其他微信身份 |
| 429 | `rate_limited` | 请求频率超过限制 |
| 503 | `sms_unavailable` | 生产短信能力未配置 |

客户端只按稳定错误码决策，不解析中文错误文案。

## 7. 数据迁移与兼容

- `mp_data_requests` 通过幂等迁移创建，不修改既有业务表字段。
- 会话轮换逻辑兼容现有令牌格式；旧令牌在用户下次登录后失效。
- 生产库中已经存在的重复、孤立和无医生会话不由应用启动自动删除，避免未经确认的大范围数据修改。
- 部署时另行执行只影响 `mp_sessions` 的审计清理脚本，并在事务前后输出聚合计数。
- 已存在的公开上传文件保持可读兼容，生产迁移完成后再关闭旧静态路径。
- 邀请网页仍可使用，但匿名用户必须完成短信验证；短信不可用期间应从微信小程序进入。

## 8. 测试策略

### 8.1 后端测试

- 登录缺少或使用无效医生时不创建会话。
- 同一 OpenID 连续和并发登录后只有最后一个令牌有效。
- 已绑定人员登录能正确解析当前医生下患者。
- 换绑验证失败时原绑定和原令牌不变。
- 换绑成功时人员、患者和令牌一次性切换。
- 邀请仅凭令牌和手机号不能修改患者。
- 匹配的 Bearer/网页会话可以提交邀请，手机号不匹配被拒绝。
- 有效短信凭证只能使用一次。
- AI 缺少认证、授权或超过限频时被拒绝。
- 上传缺少认证、医生不匹配、患者不匹配或超过限频时被拒绝。
- 上传后的文件不能通过公开静态 URL 直接读取。
- 数据申请要求绑定身份，重复申请保持幂等。

### 8.2 小程序测试

- 首页两个生命周期并发时只发起一次登录。
- 登录等待 bootstrap 医生完成。
- 问诊和 AI 发送前恢复认证，401 不产生伪成功消息。
- AI 首次发送要求授权，拒绝时不产生网络请求。
- 换绑页面不预先解除旧绑定。
- 生产模式不展示短信备用入口。
- 退出和身份轮换清理旧账号缓存。
- storage 中不存在完整身份证号、完整手机号和完整 AI 正文。

### 8.3 完整验证

- 运行后端账号、AI、邀请、上传、数据申请相关测试。
- 运行小程序类型检查和 UI 测试。
- 重新生成微信小程序生产构建并执行配置补丁。
- 扫描构建产物，不得包含测试服务器地址、模拟账号或短信备用文案。
- 本地模拟登录、绑定、换绑、邀请、AI、问诊和上传主流程。

## 9. 实施顺序

1. 先用失败测试固定登录、换绑和邀请漏洞。
2. 修复后端身份事务和会话轮换。
3. 修复客户端初始化单飞、认证恢复和原子换绑交互。
4. 加固 AI、问诊、上传和限频。
5. 实现数据申请与敏感缓存收敛。
6. 完成全量回归和生产构建检查。
7. 输出独立的生产部署、数据库清理和回滚清单，等待部署确认。

## 10. 上线边界

本设计批准后只修改本地工作区并完成验证，不自动连接生产服务器执行写操作。正式部署必须再次确认，并至少包含：

- 数据库备份及恢复演练。
- 幂等迁移执行。
- 线上 AI 认证文件同步。
- 旧会话聚合清理。
- 旧公开上传文件迁移。
- Nginx 与 Node 监听范围复核。
- 部署后真实微信登录、绑定、邀请、AI 和上传冒烟测试。
